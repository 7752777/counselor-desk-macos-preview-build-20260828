# v4.9.2 桌面授权网络修复记录

更新时间：2026-08-27

## 问题定位

用户截图中的错误是：

```text
LICENSE_SERVICE_NETWORK_FAILED
```

这不是兑换码业务校验失败。错误发生在桌面端 IPC 请求授权服务的网络阶段，因此客户端还没有拿到服务端的“兑换码无效”或“兑换成功”结果。

复核发现，当前源码已经在 23:16 更新，但此前 `r14` 的 `app.asar` 在 21:35 生成，仍然包含旧的 Node `fetch` 实现。换句话说，服务器可以正常工作，源码也已经修复，但用户安装的交付包没有包含修复。

## 修复内容

桌面主进程的授权请求改用 Electron `net.request`：

- 请求仍限制在已配置的 HTTPS 授权服务和 `/api/v1/` 路径；
- 使用 Electron Chromium 网络栈，兼容系统代理和系统证书信任配置；
- 保留 20 秒超时、响应大小限制、跳转拒绝和明确的网络/TLS/超时错误分类；
- 不把激活码、许可证私钥或模型 API Key写入客户端配置。

## 验证结果

本机使用重新打包的 Windows x64/ARM64 `app.asar` 完成以下验证：

- 包内 `desktop/main.cjs` 包含 `net.request`；
- `pnpm exec node tests/desktop-packaged-smoke.js` 通过；
- 启动打包后的 Electron 并调用公网健康检查，通过；
- 提交结构正确但伪造的兑换码，收到服务端明确的 `REDEMPTION_CODE_INVALID`，证明请求已经到达授权服务而不是在本机网络层失败；
- `node tests/electron-surface.js`、`pnpm lint` 和 `git diff --check` 通过。

## 分发边界

此前的 `r14` 桌面包不包含本次主进程网络修复，不能继续发给遇到该错误的用户。当前 Windows 新产物已从工作区的 `output/desktop/` 重新分发；macOS Universal 产物本轮未重新生成，后续必须在 macOS CI 或 macOS 实机重新生成后再替换旧 Mac 包。版本号仍为 `4.9.2`，这是同版本直接重发修复包，不应伪装成软件内自动更新。

如果新包在另一台设备仍失败，应先让用户直接打开健康地址并记录具体错误码。若健康地址本身无法访问，则是该用户网络、DNS、代理或安全策略问题，不能通过重新输入兑换码解决；应保留错误信息后再处理网络环境。
